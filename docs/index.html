Start Here

thekaziomar/laravel-atomic-cache is a production-ready caching engine for Laravel applications. Built for Laravel 10.x, 11.x, 12.x, and 13.x, it solves four common headaches: cache stampedes during traffic spikes, crashes when using cache tags on non-Redis stores, stale data left behind when database transactions fail, and memory exhaustion from large payloads.

Laravel 10 / 11 / 12 / 13.x PHP 8.2+ (tested on 8.2, 8.3, 8.4 & 8.5) Works on Redis, File, Database & SQLite
Drop-in Familiarity: You do not need to rewrite your application. Use your existing Eloquent queries and repositories. AtomicCache handles fingerprinting, mutex locking, compression, and commit-safe invalidation behind the scenes.

Why AtomicCache?

Consider an e-commerce platform running on Laravel with 25,000 products, active seasonal promotions, and thousands of concurrent buyers. Under low traffic, standard Cache::remember() works fine. But under real-world production load, four core failures often emerge:

1. Midnight Stampede (Dogpiling)

When the 1-hour cache expires at midnight and 1,200 shoppers visit the home page, all 1,200 requests hit MySQL at the exact same millisecond to recalculate the same list. Database connections saturate, response times spike, and the server returns 504 Gateway Timeouts.

2. Tag Crashes on Local & Testing Environments

Developers use Cache::tags(['products']) in production with Redis. But when running tests or local development with the file or database cache driver, Laravel crashes with BadMethodCallException: This cache store does not support tagging.

3. Marketing Link Cache Fragmentation

Marketing campaigns bring traffic with query strings like ?utm_source=fb&fbclid=xyz. Standard URL caching treats each click as a brand new page, generating thousands of duplicate cache files for the exact same product and wasting RAM.

4. Memory Exhaustion on Large Catalogs

Caching a 5,000-item array or collection as one raw key strains memory buffers and hits Memcached's 1MB limit. AtomicCache partitions large datasets into safe chunks and applies Gzip compression automatically.

Who Is This For?

  • E-commerce & Marketplaces: High catalog reads, flash sales, and cart checkouts where database load must stay flat.
  • SaaS Applications: Endpoints with expensive aggregations, reports, and tenant-scoped summaries.
  • Teams on File/Database Cache: Anyone developing locally or hosting on platforms without Redis who still wants tag-based invalidation.

When NOT to Cache & Known Limitations

Caching is not suitable for all data. Avoid caching in these specific scenarios:

  • Real-time WebSockets & Chat Messages: Chat messages (e.g. ChatMessage) should be broadcasted directly via Pusher or Laravel Reverb. Caching them creates unnecessary memory churn without read benefits.
  • High-Frequency GPS & Telemetry: Live rider location updates sent every 3 seconds belong in Redis Pub/Sub, Kafka, or ClickHouse, not application-level cache.
  • Audit Ledgers & Financial Balances: Financial transactions and audit logs are write-heavy and must be queried directly from the authoritative database with row locks.

Architectural Limitations & Gotchas

1. Eloquent Mass Operations (Bypasses Model Events)

Direct query builder batch updates or deletes (e.g. Product::where(...)->update(...), delete(), insert()) do not fire Eloquent model events. Consequently, AutoClearsCache will not automatically trigger. 

// Warning: Mass query builder updates do not fire Eloquent model events:
Product::where('category_id', 5)->update(['status' => 'archived']);

// Solution 1: Use the model's static flush helper:
Product::flushCache();

// Solution 2: Clear the model table tag via facade:
AtomicCache::clearCollection('products'); // or AtomicCache::clearTags([Product::class]);

2. Pagination with Query Macros (->atomicCache())

The ->atomicCache() macro immediately terminates the query and executes ->get(), returning an Eloquent Collection. You cannot chain ->paginate() afterwards. 

// Recommended: Use HasAtomicCache in your Service Layer
// rememberCollection() automatically isolates request query strings and page numbers:
class ProductService {
    use HasAtomicCache;

    public function getActiveProducts() {
        return $this->rememberCollection('active', fn() => Product::where('status', 'active')->paginate(15), 3600);
    }
}

// Alternative: Explicit key caching with query parameters:
$page = request()->get('page', 1);
$queryHash = md5(serialize(request()->only(['page', 'per_page', 'sort', 'filter'])));
$items = AtomicCache::tags([Product::class])->remember("products:active:{$queryHash}", 3600, fn() => Product::paginate(15));

3. Invalidation Granularity on Write-Heavy Tables

AutoClearsCache automatically invalidates the entire table tag (e.g. products). For read-heavy tables (catalogs, settings, profiles), this maintains high cache hit rates without frequent invalidation. However, for write-heavy tables (e.g. live impression counters, audit logs), every insert clears the table tag. In write-heavy scenarios, use item-specific keys (e.g. AtomicCache::remember("item:{$id}", ...)) without broad table tags.

Guarantees vs Non-Guarantees

To ensure complete architectural clarity on what AtomicCache handles automatically versus what requires developer attention:

Scenario / Operation Automated by Package? Behavior & Action Required
Eloquent Model Instance Save: $product->save(), update() Yes Automatically flushes item tag (products:42), collection tag (products), and parent relations strictly on DB::afterCommit.
Model Deletes & Restores: $product->delete(), restore() Yes Automatically flushes related tags on DB::afterCommit.
Model Counters: $product->increment(), decrement() Yes Fires updated model event; automatically clears cache on commit.
Single-Level BelongsTo Parents: $cacheParents = ['store'] Yes Automatically clears child tag, scoped tag (stores:5:orders), and parent umbrella tag (stores:5).
Active Transactions: DB::transaction() Yes AtomicCache::remember() automatically bypasses cache during active transactions to prevent dirty reads and phantom cache on rollbacks.
High-Frequency Columns: $cacheIgnoreColumns Yes Updating counters (e.g. view_count) clears only the single item tag (products:5) and keeps table and parent collections warm.
Rolled-back Transactions: DB::rollBack() Yes Invalidation callbacks are deferred to afterCommit. If rollback occurs, cache is untouched.
Query Builder Mass Updates: Product::where()->update() No Eloquent events do not fire. You must manually call Product::flushCache(); or AtomicCache::clearCollection('products').
Query Builder Mass Deletes: Product::where()->delete() No Eloquent events do not fire. Call Product::flushCache(); manually.
Direct SQL / DB Facade: DB::table('products')->delete() No Bypasses Eloquent entirely. Call AtomicCache::clearCollection('products') manually.
Quiet Operations: saveQuietly(), withoutEvents() No Intentionally suppresses model events. Call $product->clearCache() manually if needed.
Pivot Table Changes: attach(), detach(), sync() No Pivot mutations do not fire model events on parent models. Call AtomicCache::clearTags(...) manually.
Multi-Level Grandparent: Item -> Order -> Store No Laravel's native $touches calls rawUpdate() which does NOT fire model events. Either manually call $orderItem->order->touch() or declare parent tags via getRelatedCacheTags().
External Database Mutations: External scripts, ETL imports No External processes outside PHP cannot trigger Laravel events. Schedule or invoke cache invalidation manually.

10-Second Quickstart

If you don't want to think about keys, tag names, or redis commands, follow these three steps:

Step 1: Add Trait to your Model

use KaziOmar\AtomicCache\Traits\AutoClearsCache;

class Product extends Model
{
    use AutoClearsCache; // Auto-clears query cache on save/delete after DB commit
}

Step 2: Append ->atomicCache() to any query

// Zero keys to manage: automatically fingerprinted and tagged with 'products' table
$products = Product::where('status', 'active')->latest()->atomicCache(3600);
$single   = Product::where('slug', $slug)->atomicCacheFirst(3600);

Step 3: Run the Model Auditor

Inspect model cache readiness and automatically detect missing traits or unsafe relations:

php artisan atomic-cache:check

Installation & Configuration

Install the package via Composer into your Laravel application: 

composer require thekaziomar/laravel-atomic-cache

Publish the optional configuration file if you need to adjust lock durations or compression thresholds: 

php artisan vendor:publish --tag="atomic-cache-config"

1. Product Catalog Queries

Scenario: Heavy Database Reads with Filters & Pagination

The Challenge: High-traffic category catalogs often repeat identical database queries thousands of times per minute. Standard manual caching requires inventing unique string keys, handling cache tag exceptions on local environments, and manually evicting keys when inventory updates.

The Solution: Append ->atomicCache() or ->atomicCacheFirst() directly to any Eloquent or Query Builder instance. A deterministic fingerprint is automatically computed, and the underlying database table is tagged for auto-invalidation.

app/Http/Controllers/ProductController.php 
// 1. LIST QUERY: Cache active products for 1 hour (3600 seconds)
$products = Product::where('status', 'active')
    ->orderBy('created_at', 'desc')
    ->atomicCache(3600);

// 2. SINGLE ITEM QUERY: Cache single product model
$product = Product::where('slug', $slug)
    ->atomicCacheFirst(3600);

Macro Method Arguments

Argument Type Default Description
$keyOrTtl string|int|null null TTL in seconds (e.g. 3600) or custom key (e.g. 'featured_deals'). Defaults to config.
$ttl ?int null TTL in seconds if custom string key was passed as argument 1.
$tags array [] Additional tags. The table name (e.g. products) is attached automatically.
$lock bool false Enable distributed locking (stampede shield) so only 1 request queries MySQL upon cache miss.
Automatic Query & Join Invalidation: The query macro generates deterministic fingerprints incorporating SQL, bindings, and active eager loads (with()). If your query joins multiple tables using standard Query Builder methods (e.g. join(), leftJoin()), AtomicCache automatically tags all joined tables so updates to any joined model safely invalidate the cached query. Note: Tables referenced in subqueries or raw SQL (joinRaw()) are not statically parsed; specify any extra tags explicitly in the $tags argument.
Pagination with ->atomicCache() vs HasAtomicCache: Calling ->atomicCache() immediately terminates the query and returns an Eloquent Collection. For paginated catalog or API endpoints, use HasAtomicCache::rememberCollection() in your Service layer (e.g. ->rememberCollection('search', fn() => Product::filter()->paginate(20))). This isolates distinct pages (?page=1, ?page=2) into their own cache partitions and caches the complete LengthAwarePaginator object.

2. Flash Sale Concurrency

Scenario: 5,000 Concurrent Buyers vs 10 Limited Inventory Items

The Challenge: When a flash sale goes live, thousands of buyers refresh the product page at once. If cache expires, they all hit MySQL at the same second (Cache Stampede). Furthermore, during checkout, race conditions can cause negative stock and overselling.

The Solution: Use AtomicCache::rememberWithLock() for high-concurrency read shields, and pair with database pessimistic row locking (lockForUpdate()) for write transactions.

app/Http/Controllers/FlashSaleController.php 
// 1. READ SHIELD: Collapses concurrent traffic to 1 query while caching
public function showDeal(int $productId)
{
    return AtomicCache::rememberWithLock("flash_deal:{$productId}", 300, function () use ($productId) {
        return Product::where('id', $productId)->firstOrFail();
    }, lockSeconds: 10, waitSeconds: 5);
}

// 2. WRITE SHIELD: Safe checkout with auto-invalidation on commit
public function checkout(int $productId, int $userId)
{
    return DB::transaction(function () use ($productId, $userId) {
        $product = Product::where('id', $productId)->lockForUpdate()->firstOrFail();

        if ($product->stock < 1) {
            return response()->json(['error' => 'Sold out!'], 422);
        }

        $product->stock -= 1;
        $product->save(); // AutoClearsCache purges the 'products' cache immediately after DB commit
        $order = Order::create(['product_id' => $productId, 'user_id' => $userId]);

        return response()->json(['success' => true, 'order_id' => $order->id]);
    });
}
Note: AutoClearsCache listens to model created, updated (including $model->decrement() / $model->increment()), and deleted events. Only direct database mass queries that bypass Eloquent models entirely (e.g. DB::table('products')->decrement() or Product::where(...)->update()) require manually calling Product::flushCache() or AtomicCache::clearCollection('products').

3. User Dashboard & Cart

Scenario: Authenticated Cart & Personalized Navigations

The Challenge: Developers accidentally store user data globally, causing User A to see User B's cart, or write awkward concatenation like Cache::get('user_' . $userId . '_cart').

The Solution: Use AtomicCache::rememberForUser(). It automatically scopes keys under atomic:user:{userId}:{key}, preventing cross-user data leakage.

app/Http/Controllers/CartController.php 
// Automatically scopes to "atomic:user:{id}:active_cart" (supports int, UUID, and ULID)
$cart = AtomicCache::rememberForUser('active_cart', 1800, function () {
    return Cart::with('items.product')->where('user_id', auth()->id())->first();
});

4. Model Invalidation on Commit

Scenario: Shopping Cart Checkout & Transaction Rollback Protection

The Challenge: When clearing caches inside a database transaction, if the transaction later rolls back (e.g. payment fails), your cache was prematurely destroyed or left in an inconsistent state.

The Solution: AutoClearsCache listens to Eloquent events and queues all tag invalidations to execute strictly inside DB::afterCommit(). If a transaction rolls back, your cache is 100% untouched.

app/Models/Product.php 
use KaziOmar\AtomicCache\Traits\AutoClearsCache;

class Product extends Model
{
    use AutoClearsCache;

    // Automatically flushes additional related tags on commit:
    protected array $relatedCacheTags = ['catalog', 'home_feed'];
}

Declarative Parent Invalidation ($cacheParents)

Similar in spirit to Laravel's native $touches = ['store']; (operating on a single-level BelongsTo relation), you can link parent relationships declaratively. When an order is created, modified, or restored, AtomicCache automatically calculates and flushes the parent store's cache without manual string construction or typo risks:

app/Models/Order.php 
use Illuminate\Database\Eloquent\Relations\BelongsTo;
use KaziOmar\AtomicCache\Traits\AutoClearsCache;

class Order extends Model
{
    use AutoClearsCache;

    // Automatically flushes parent store caches on commit (supports $cacheParents, or aliases $cacheTouches / $clearsRelations)
    protected array $cacheParents = ['store'];

    public function store(): BelongsTo
    {
        return $this->belongsTo(Store::class);
    }
}
Dirty Foreign Key & Ghost Data Protection: If an order is transferred from Store #1 to Store #2 ($order->store_id = 2), AtomicCache tracks original model attributes and automatically invalidates cache tags for both the former store (#1) and the new store (#2).
Important Limitation on Grandparents & Laravel $touches: Multi-level hierarchies (e.g. OrderItem -> Order -> Store) do not cascade 2+ levels deep automatically. Crucially, Laravel's native protected $touches = ['order']; property runs a raw database update (rawUpdate) and does NOT fire Eloquent model events. Consequently, declaring $touches will not trigger parent cache invalidation!
Solution 1 (Recommended): Define explicit grandparent tags via getRelatedCacheTags():
public function getRelatedCacheTags(): array {
    return ["stores:{$this->order->store_id}:orders", "stores:{$this->order->store_id}"];
}
Solution 2: Call $orderItem->order->touch() directly on the model instance (which calls save() and fires updated).

Model-Level Manual Flush Helpers (flushCache & clearCache)

AutoClearsCache provides two helper methods directly on the model for manual cache invalidation:

Manual Invalidation Example 
// 1. Instance helper: manually clear this record and its parent tags
$product = Product::find(42);
$product->clearCache(); // Expressive alias for clearModelCacheOnCommit()

// 2. Static helper: flush all collection-level caches for this model's table
Product::where('category_id', 5)->update(['discount' => 10]);
Product::flushCache(); // Wipes all "products" table collection caches in one line!
Scope & Transaction Note: Product::flushCache() invalidates the model's table collection tag (products). It does not invalidate individual item tags (products:42) or parent-scoped tags (stores:5:orders). Also, unlike lifecycle events that wait for commit, Product::flushCache() executes immediately. Inside transactions, wrap in DB::afterCommit(fn() => Product::flushCache()).

High-Frequency Column Protection ($cacheIgnoreColumns)

When updating high-frequency analytics or counters (e.g. view_count, last_login_at), flushing the entire collection cache (products) creates unnecessary churn. Declaring $cacheIgnoreColumns ensures that collection and parent caches remain warm, while only the single item cache (products:42) is cleared:

app/Models/Product.php 
class Product extends Model
{
    use AutoClearsCache;

    protected array $cacheParents = ['store'];

    // Updating view_count or meta will NOT wipe the 'products' table collection cache
    protected array $cacheIgnoreColumns = ['view_count', 'meta'];
}

Transaction-Safe Bulk Invalidation (AtomicCache::invalidating)

Wrap bulk operations and direct SQL executions so that cache invalidation is deferred to afterCommit if executed inside an active database transaction:

Bulk Invalidation Wrapper 
AtomicCache::invalidating([Order::class, Product::class], function () {
    DB::table('orders')->where('status', 'draft')->delete();
    DB::table('products')->where('stock', 0)->update(['status' => 'out_of_stock']);
});
🏷️ Cache Key vs Cache Tag Cheat-Sheet
What are you caching? Service Cache Tag Model Declaration
All Products List ['products'] use AutoClearsCache;
Single Product by ID ['products:5', 'products'] use AutoClearsCache;
Store's Orders List ['stores:5:orders', 'stores:5'] $cacheParents = ['store'];
Category's Products ['categories:3:products', 'categories:3'] $cacheParents = ['category'];

5. Service Layer Architecture

Scenario: Standardized Repository & Service Layer Caching

Standardize caching across your business layer with HasAtomicCache. It provides structured methods (rememberItem, rememberCollection) and safely normalizes complex arguments:

app/Services/ProductService.php 
use KaziOmar\AtomicCache\Traits\HasAtomicCache;

class ProductService
{
    use HasAtomicCache;

    protected int $cacheTTL = 3600;
    protected string $cacheResource = 'products';

    // 1. Single item: tags "products:42" AND "products"
    public function find(int $id)
    {
        return $this->rememberItem($id, fn() => Product::findOrFail($id));
    }

    // 2. Collection: tags "products", automatically sanitizes marketing tags
    public function search(array $filters)
    {
        return $this->rememberCollection('search', function () use ($filters) {
            return Product::filter($filters)->paginate(20);
        }, extraArgs: $filters);
    }
}
Marketing Tag Sanitization & Pagination Isolation: In rememberCollection, AtomicCache automatically strips ad tracking parameters (utm_*, fbclid, gclid, etc.) before computing the cache key. Legitimate query params (?page=2, ?sort=price) remain safely cached in their own isolated partitions.

6. Blade Fragment Caching

Scenario: Heavy View Rendering in Navigation Menus & Sidebars

The Challenge: Multi-level category trees and megamenus require rendering dozens of nested HTML elements. Re-rendering this on every HTTP request burns CPU cycles even when database results are cached.

The Solution: Use @atomicCache directly in your Blade views to cache the rendered HTML markup.

resources/views/partials/navigation.blade.php 
{{-- Caches rendered HTML for 3600 seconds, tagged with 'categories' --}}
@atomicCache('sidebar_categories', 3600, ['categories'])
    <div class="category-menu">
        @foreach(Category::with('children')->get() as $category)
            <h4>{{ $category->name }}</h4>
            @foreach($category->children as $child)
                <span>{{ $child->name }}</span>
            @endforeach
        @endforeach
    </div>
@endAtomicCache
⚠️ Important Security Note: Blade fragment caching is global across all visitors. Never cache personalized or user-specific content (such as logged-in user names, personal shopping carts, or @csrf tokens) in a generic fragment block. If user-scoping is needed, append the user ID to the cache key (e.g. @atomicCache('user_nav_' . auth()->id(), 3600)).

Compression, Chunking & Internals

1. Auto Payload Compression (Gzip > 50KB)

When serialized data exceeds 50KB, AtomicCache compresses it using gzcompress before storing. This reduces Redis/Memcached memory consumption by up to 70–80% (actual savings depend on payload structure and entropy) and decompresses transparently on retrieval.

2. Transparent Chunking with Dynamic Sizing & Generation UUIDs

Large collections or arrays (1,000+ items) are partitioned into safe chunk keys ({key}:__chunk__:{generation}:{i}). Chunks are written under a unique generation UUID before the atomic manifest is updated, eliminating torn-read race conditions for concurrent readers. Payloads are dynamically sampled to stay strictly under 800 KB (max_bytes) for Memcached 1MB safety. When fetched, all chunks are retrieved in a single batch request via Redis MGET (or multi-key read on file/database drivers). Prior chunks expire via store TTL, or can be eagerly purged on non-chunked overwrites by opting into clean_on_put.

3. Write Deduplication (Cache DNA)

Payloads are hashed before writing (Cache DNA). When enabled (ATOMIC_CACHE_DEDUPLICATION_ENABLED=true), if identical content is already cached with valid remaining TTL, AtomicCache skips CPU-intensive gzip compression and chunk re-splitting, refreshing the expiration TTL on the existing item and chunks in the cache store.

4. Expiry Jitter (withJitter)

Prevents herd expiry spikes when thousands of keys share the same TTL by adding random variance. Note: The fluent method takes a decimal fraction (e.g. 0.05 for ±5% or 0.10 for ±10%), whereas the ATOMIC_CACHE_JITTER_PERCENTAGE .env variable accepts an integer percentage (e.g. 5): 

AtomicCache::withJitter(0.05)->remember('popular_feed', fn() => getFeed(), 3600);

5. Optimistic Concurrency Control (OCC)

AtomicCache captures tag version tokens before and after invoking remember closures. If another process invalidates tags while a slow computation is executing, the stale result is safely discarded instead of polluting freshly cleared cache keys.

6. HTTP Query Limits (DoS & Hash Collision Protection)

Incoming requests with more than 20 query parameters (max_params) or exceeding 2,048 bytes (max_bytes) cleanly bypass the cache, executing directly against the database to protect against hash collision attacks and memory exhaustion.

7. Type-Safe Model Tags

Pass Model classes directly to eliminate typos and unlock IDE autocompletion & refactoring safety: 

// 1. Pass Model classes:
AtomicCache::tags([Product::class, Category::class])->remember('catalog', fn() => ..., 3600);

// 2. Pass Model instances (auto-tags "products:12" and "products"):
AtomicCache::tags([$product, 42])->remember('deal', fn() => ..., 3600);

// 3. Clear tags using Model classes:
AtomicCache::clearTags([Product::class, 42]);

Zero-Crash Virtual Tagging

In standard Laravel, calling Cache::tags() on the file or database driver throws an immediate exception. AtomicCache implements a transparent Virtual Tag Engine:

  1. Each tag maintains a unique UUID version token in the store: atomic:__tag_v__:{tag}.
  2. Keys incorporate an MD5 hash of their sorted tag tokens: {key}:vt:md5(sorted_tokens).
  3. Calling AtomicCache::clearTags(['products']) generates a fresh UUID token in the store atomically.
  4. Existing cached entries become instant cache misses in 0 milliseconds without running slow directory scans or SQL deletes. Note on File Driver: On Redis/Memcached, orphan entries expire automatically via store TTL. On the local file driver, orphan cache files remain on disk until their TTL expires or until php artisan cache:clear / cache prune is executed.

Troubleshooting & FAQ

Diagnose and resolve the most common caching questions, architectural gotchas, and invalidation behaviors.

1 The cache is not cleared after updating data

AtomicCache automatically invalidates tags via Eloquent model events (created, updated, deleted, restored). If your cache remains stale, verify these 5 common causes:

A. Mass Updates via Query Builder: Direct query builder calls like Product::where('status', 'active')->update(...) or delete() bypass Eloquent model events.
Fix: Call AtomicCache::clearTags([Product::class]); manually after mass updates.
B. Silent Model Operations: Methods like ->saveQuietly(), updateQuietly(), and deleteQuietly() suppress all events.
Fix: Call ->clearModelCacheOnCommit(); or flush tags explicitly.
C. Many-to-Many / Pivot Updates: Operations like ->roles()->sync(...), attach(), or detach() modify pivot tables without firing parent model events.
Fix: Call AtomicCache::clearTags([User::class, 'roles']); after syncing.
D. Direct Database / Raw SQL: DB::table('products')->where(...)->update(...) operates outside Eloquent.
Fix: Always purge tags with AtomicCache::clearTags(['products']);.
E. Database Transaction Rollback: AtomicCache registers cache clearing via afterCommit(). If a transaction rolls back, cache is intentionally preserved to maintain integrity.

2 The cache never hits (always a cache miss)

If database queries are executing repeatedly despite caching macros:

A. Dynamic / Non-deterministic Query Bindings: Queries incorporating dynamic timestamps (e.g. where('created_at', '<=', now())) generate a brand-new SQL fingerprint every second.
Fix: Round timestamps to 5-minute or 1-hour boundaries: now()->startOfHour().
B. Exceeding HTTP Query Parameter Limits (DoS Protection): In HasAtomicCache, requests with more than 20 query parameters or exceeding 2,048 bytes intentionally bypass caching.
Fix: Customize query limits in config/atomic-cache.php: query_limits.max_params.

3 Common Architectural Questions

Q: Can circular relationships in cause infinite loops?
No. Parent relation resolution strictly inspects BelongsTo relationships and resolves foreign keys on the current model in memory. It does not re-save parent models or trigger recursive model events.
Q: What happens if Redis goes down?
AtomicCache catches store connection exceptions gracefully. If Redis becomes unavailable, execution falls back to calculating the original closure without crashing user requests, logging an alert to Laravel logs.
Q: How does multi-tenancy work with native Redis tags?
When using Redis native tags (TaggedCache), Laravel's underlying tag set key (tag:orders:entries) is not prefixed by runtime prefixes unless the Redis store connection has a dedicated prefix. In single-Redis shared databases, calling AtomicCache::clearTags(['orders']) in Tenant A flushes orders in Tenant B as well (over-invalidation, not data leakage). To achieve complete tag isolation across tenants in Redis, assign each tenant a dedicated Redis database or connection prefix.
Q: What happens if Redis allkeys-lru evicts OCC version tokens?
AtomicCache stores OCC version tokens with forever(). If Redis runs out of memory under an allkeys-lru eviction policy, Redis may evict version tokens. When evicted, the next access generates a fresh UUID token. This safely forces a cache miss (preventing stale data), though it may cause a temporary rise in cache miss rates until repopulated.

A quick reference to common AtomicCache methods and operations:

Method Signature Return Behavior & Description
1. Core Remember & Cache Operations
remember($key, $callback, $ttl = null, $tags = []) mixed Standard cache remember with compression, chunking, and jitter (defaults to configured TTL).
rememberWithLock($key, $ttl, $callback, $tags = [], $lockSec = 10, $waitSec = 5) mixed Atomic distributed locking (anti-stampede shield) for high-traffic read operations.
rememberForUser($key, $ttl, $callback, $userId = null, $tags = []) mixed Scopes key to atomic:user:{id}:{key} for safe multi-tenant caching.
get($key, $default = null, $tags = []) mixed Retrieve item with automatic chunk reassembly and Gzip decompression.
put($key, $value, $ttl = null, $tags = []) bool Store item with transparent compression, chunking, and jitter.
has($key, $tags = []) bool Check if a valid, unexpired key exists in the active cache store.
forever($key, $value, $tags = []) bool Store item with 10-year long-term TTL (315,360,000s) for permanent lookup dictionaries.
pull($key, $default = null, $tags = []) mixed Retrieve item and immediately delete it from store (flash data).
forget($key, $tags = []) / clear($key) bool Remove an individual item from cache store.
flush() bool Completely wipe all stored keys from active cache repository.

Global Helper: atomic_cache()

Use the global helper function directly without importing the Facade: 

// 1. Retrieve value or remember
$data = atomic_cache('homepage_banners', 3600, fn() => Banner::all());

// 2. Call fluent builder directly
$data = atomic_cache()->tags([Product::class])->remember('deals', 600, $callback);

Configure any package setting globally in your application's .env file:

Variable Key Default Description
ATOMIC_CACHE_ENABLED true Master switch to enable or disable atomic caching globally.
ATOMIC_CACHE_DEFAULT_TTL 3600 Default cache lifetime in seconds (1 hour).
ATOMIC_CACHE_STORE null Specific cache store (e.g. redis, file). Defaults to Laravel's default store.
ATOMIC_CACHE_PREFIX atomic Global key prefix namespace.
ATOMIC_CACHE_STAMPEDE_ENABLED true Enables distributed mutex locking during cache recomputations.
ATOMIC_CACHE_LOCK_SECONDS 10 Maximum duration in seconds a distributed lock is held before automatic release.
ATOMIC_CACHE_WAIT_SECONDS 5 Maximum seconds concurrent requests wait to acquire lock before computing fallback.
ATOMIC_CACHE_COMPRESSION_ENABLED true Enables automatic Gzip payload compression.
ATOMIC_CACHE_COMPRESSION_THRESHOLD 51200 Minimum payload size in bytes to trigger Gzip compression (50 KB).
ATOMIC_CACHE_COMPRESSION_LEVEL 6 Gzip compression level from 1 (fastest) to 9 (maximum compression).
ATOMIC_CACHE_CHUNKING_ENABLED true Enables transparent chunking for mega collections.
ATOMIC_CACHE_CHUNKING_THRESHOLD 1000 Item count required to partition collections into chunks (triggers on more than 1,000 items or when payload exceeds max_bytes).
ATOMIC_CACHE_CHUNK_SIZE 1000 Maximum items per partition chunk.
ATOMIC_CACHE_CHUNK_MAX_BYTES 800000 Maximum payload size in bytes per chunk (800 KB) for strict Memcached 1MB limit safety.
ATOMIC_CACHE_CHUNKING_CLEAN_ON_PUT false When true, eagerly purges prior generation chunks upon non-chunked key overwrite.
ATOMIC_CACHE_DEDUPLICATION_ENABLED false Opt-in DNA hashing: skips re-compression and chunk re-splitting if identical content is cached.
ATOMIC_CACHE_QUERY_MAX_PARAMS 20 Maximum query string parameters allowed before automatically bypassing cache (DoS protection).
ATOMIC_CACHE_QUERY_MAX_BYTES 2048 Maximum query string byte size allowed before bypassing cache (prevents hash collision attacks).
ATOMIC_CACHE_JITTER_ENABLED false Enables random variance on expiry time to prevent simultaneous expiry (thundering herd).
ATOMIC_CACHE_JITTER_PERCENTAGE 5 Percentage variance applied to TTL when jitter is enabled (±5%).
ATOMIC_CACHE_SELF_HEALING_ENABLED true Automatically purges corrupted or orphaned chunk keys and self-heals cleanly.
ATOMIC_CACHE_LOG_CORRUPTED true Logs corrupted cache recovery events to standard Laravel application logs.
