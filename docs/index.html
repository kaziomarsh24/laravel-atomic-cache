Docs / Getting Started / Introduction

Introduction

thekaziomar/laravel-atomic-cache is an open-source caching engine for Laravel applications. Built for Laravel 10.x, 11.x, 12.x, and 13.x, it solves four common headaches: cache stampedes during traffic spikes, crashes when using cache tags on non-Redis stores, stale data left behind when database transactions fail, and memory exhaustion from large payloads.

Laravel 10 / 11 / 12 / 13.x PHP 8.2+ (tested on 8.2, 8.3, 8.4 & 8.5) Works on Redis, File, Database & SQLite
Drop-in Familiarity: You do not need to rewrite your application. Use your existing Eloquent queries and repositories. AtomicCache handles fingerprinting, mutex locking, compression, and commit-safe invalidation behind the scenes.

Why AtomicCache?

Consider an e-commerce platform running on Laravel with 25,000 products, active seasonal promotions, and thousands of concurrent buyers. Under low traffic, standard Cache::remember() works fine. But under real-world production load, four core failures often emerge:

1. Midnight Stampede (Dogpiling)

When the 1-hour cache expires at midnight and 1,200 shoppers visit the home page, all 1,200 requests hit MySQL at the exact same millisecond to recalculate the same list. Database connections saturate, response times spike, and the server returns 504 Gateway Timeouts.

2. Tag Crashes on Local & Testing Environments

Developers use Cache::tags(['products']) in production with Redis. But when running tests or local development with the file or database cache driver, Laravel crashes with BadMethodCallException: This cache store does not support tagging.

3. Marketing Link Cache Fragmentation

Marketing campaigns bring traffic with query strings like ?utm_source=fb&fbclid=xyz. Standard URL caching treats each click as a brand new page, generating thousands of duplicate cache files for the exact same product and wasting RAM.

4. Memory Exhaustion on Large Catalogs

Caching a 5,000-item array or collection as one raw key strains memory buffers and hits Memcached's 1MB limit. AtomicCache partitions large datasets into safe chunks and applies Gzip compression automatically.

Who Is This For?

  • E-commerce & Marketplaces: High catalog reads, flash sales, and cart checkouts where database load must stay flat.
  • SaaS Applications: Endpoints with expensive aggregations, reports, and tenant-scoped summaries.
  • Teams on File/Database Cache: Anyone developing locally or hosting on platforms without Redis who still wants tag-based invalidation.

When NOT to Cache

Caching is not suitable for all data. Avoid caching in these situations:

  • Real-time WebSockets & Chat Messages: Chat messages (e.g. ChatMessage) should be broadcasted directly via Pusher or Laravel Reverb. Caching them creates unnecessary memory churn without read benefits.
  • High-Frequency GPS & Telemetry: Live rider location updates sent every 3 seconds belong in Redis Pub/Sub, Kafka, or ClickHouse, not application-level cache.
  • Audit Ledgers & Financial Balances: Financial transactions and audit logs are write-heavy and must be queried directly from the authoritative database with row locks.

10-Second Quickstart

If you don't want to think about keys, tag names, or redis commands, follow these two steps:

Step 1: Add Trait to your Model

use KaziOmar\AtomicCache\Traits\AutoClearsCache;

class Product extends Model
{
    use AutoClearsCache; // Auto-clears query cache on save/delete after DB commit
}

Step 2: Append ->atomicCache() to any query

// Zero keys to manage: automatically fingerprinted and tagged with 'products' table
$products = Product::where('status', 'active')->latest()->atomicCache(3600);
$single   = Product::where('slug', $slug)->atomicCacheFirst(3600);

Installation & Configuration

terminal 
composer require thekaziomar/laravel-atomic-cache

Publish the optional configuration file if you need to adjust lock durations or compression thresholds:

terminal 
php artisan vendor:publish --tag="atomic-cache-config"

1. Product Catalog Queries

Scenario: Heavy Database Reads with Filters & Pagination

The Problem: When customers browse your catalog, filter by categories, or paginate through results, recalculating complex SQL joins on every request strains the database server.

The Solution: Append ->atomicCache() to any Eloquent query. It automatically hashes the SQL statement and bindings into a unique fingerprint, tags it with the table name (products), and returns cached results.
app/Http/Controllers/ProductController.php 
// 1. Cache filtered product collection for 1 hour (3600 seconds)
$products = Product::where('is_active', true)
    ->where('category_id', $categoryId)
    ->orderBy('price', 'asc')
    ->atomicCache(3600);

// 2. Cache a single product detail with stampede lock protection
$product = Product::where('slug', $slug)
    ->atomicCacheFirst(3600, lock: true);
Parameter Type Default Behavior
$keyOrTtl int | string | null null Pass an integer like 3600 to set TTL with automatic SQL fingerprinting. Or pass a custom key name. If null, uses default config TTL.
$ttl int | null null Explicit TTL in seconds if you passed a custom string key in the 1st parameter.
$tags array [] Additional tags. The table name (e.g. products) is attached automatically.
$lock bool false Enable distributed locking (stampede shield) so only 1 request queries MySQL upon cache miss.

Automatic Query & Join Invalidation

The query macro generates deterministic fingerprints incorporating SQL, bindings, and active eager loads (with()). If your query joins multiple tables (e.g. users join orders), AtomicCache automatically tags both tables so updates to either model safely invalidate the cached query.

2. Flash Sale Concurrency

Scenario: 5,000 Concurrent Buyers vs 10 Limited Inventory Items

The Problem: When a flash sale goes live, thousands of buyers refresh the product page at once. If cache expires, they all hit MySQL at the same second (Cache Stampede). Furthermore, during checkout, race conditions can cause negative stock and overselling.

The Recommendation: Use AtomicCache::rememberWithLock() for high-concurrency read shields, and pair with database pessimistic row locking (lockForUpdate()) for write transactions.
app/Http/Controllers/FlashSaleController.php 
// 1. READ SHIELD: Collapses concurrent traffic to 1 query while caching
public function showDeal(int $productId)
{
    return AtomicCache::rememberWithLock("flash_deal:{$productId}", 300, function () use ($productId) {
        return Product::where('id', $productId)->firstOrFail();
    }, lockSeconds: 10, waitSeconds: 5);
}

// 2. WRITE SHIELD: Safe checkout with auto-invalidation on commit
public function checkout(int $productId, int $userId)
{
    return DB::transaction(function () use ($productId, $userId) {
        $product = Product::where('id', $productId)->lockForUpdate()->firstOrFail();

        if ($product->stock < 1) {
            return response()->json(['error' => 'Sold out!'], 422);
        }

        $product->stock -= 1;
        $product->save(); // AutoClearsCache purges the 'products' cache immediately after DB commit
        $order = Order::create(['product_id' => $productId, 'user_id' => $userId]);

        return response()->json(['success' => true, 'order_id' => $order->id]);
    });
}
Note: Eloquent lifecycle events fire on $model->save(), create(), and delete(). If using direct query methods like $product->decrement('stock', 1) or mass updates, manually call AtomicCache::clearTags(['products']).

3. User Dashboard & Cart

Scenario: Private Customer Data Isolation

The Problem: When caching user carts, order histories, or notification counters, using a global key creates critical security risks where Customer A sees Customer B's cart.

The Solution: Use AtomicCache::rememberForUser() or the fluent AtomicCache::forUser() builder. It automatically namespaces the key with the authenticated user ID (supporting integer IDs, UUIDs, and ULIDs) and can be forgotten cleanly on logout or checkout.
app/Http/Controllers/CartController.php 
// 1. Remember cart for active user (key: "atomic:user:{auth_id}:active_cart")
$cart = AtomicCache::rememberForUser('active_cart', 600, function () {
    return Cart::where('user_id', auth()->id())->with('items')->first();
});

// 2. Invalidate private user cart after checkout
public function completeCheckout()
{
    // Forgets the scoped key "atomic:user:{auth_id}:active_cart" for the current customer
    AtomicCache::forUser()->forget('active_cart');
}

4. Model Invalidation on Commit

Scenario: Catalog Updates and Database Transaction Safety

The Problem: If an admin updates a product price inside a database transaction, but a third-party payment or billing API fails and rolls back the transaction, conventional model observers flush the cache anyway. Shoppers then see stale or corrupted prices.

The Solution: The AutoClearsCache trait connects to model events strictly inside DB::afterCommit(). If a transaction rolls back, your cache remains untouched. When it succeeds, all related tags purge automatically.
app/Models/Product.php 
namespace App\Models;

use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\SoftDeletes;
use KaziOmar\AtomicCache\Traits\AutoClearsCache;

class Product extends Model
{
    use AutoClearsCache, SoftDeletes;

    // 1. Static related tags to flush when any product changes
    protected array $relatedCacheTags = ['homepage_featured', 'catalog_filters'];

    // 2. Dynamic related tags (based on model properties)
    public function getRelatedCacheTags(): array
    {
        return [
            "stores:{$this->store_id}:products",
            "categories:{$this->category_id}",
        ];
    }
}

5. Service Layer Architecture

Scenario: Clean Encapsulation in Repositories and Services

The Recommendation: In enterprise Laravel codebases, caching logic should not clutter controllers. The HasAtomicCache trait gives services declarative argument hashing and granular item vs collection invalidation.
app/Services/CatalogManager.php 
namespace App\Services;

use KaziOmar\AtomicCache\Traits\HasAtomicCache;
use App\Models\Product;

class CatalogManager
{
    use HasAtomicCache;

    // Explicitly define resource tag so it invalidates with the 'products' table
    protected string $cacheResource = 'products';
    protected int $cacheTTL = 3600;

    // Flavor 1: Declarative argument hashing
    public function searchProducts(string $query, int $limit = 20)
    {
        $callback = fn() => Product::where('name', 'like', "%{$query}%")->take($limit)->get();
        return $this->cache(__FUNCTION__, func_get_args(), $callback);
    }

    // Flavor 2: Granular item vs collection caching
    public function find(int $id)
    {
        return $this->rememberItem($id, fn() => Product::findOrFail($id));
    }

    public function update(int $id, array $data)
    {
        $product = Product::findOrFail($id);
        $product->update($data);

        // Precise invalidation:
        $this->forgetItem($id);       // Flushes single item tag "products:{$id}"
        $this->flushCollection();     // Flushes list queries under "products" tag

        return $product;
    }
}

Marketing Tag Sanitization (Cache Fragmentation Shield)

When users visit with ad campaign tags like ?page=2&fbclid=xyz&utm_source=fb, methods like cache() and rememberCollection() automatically strip tracking parameters before calculating the cache fingerprint. Legitimate filter parameters (?page=2, ?sort=price) remain isolated and sorted with ksort(), but 10,000 ad clicks share the exact same cache entry instead of duplicating memory.

6. Blade Fragment Caching

Scenario: Heavy View Rendering in Navigation Menus & Sidebars

The Problem: Multi-level category trees and megamenus require rendering dozens of nested HTML elements. Re-rendering this on every HTTP request burns CPU cycles even when database results are cached.

The Solution: Use @atomicCache to cache the fully rendered HTML string directly in Blade.
resources/views/partials/navigation.blade.php 
{{-- Caches rendered HTML for 3600 seconds, tagged with 'categories' --}}
@atomicCache('sidebar_categories', 3600, ['categories'])
    <div class="category-menu">
        @foreach(Category::with('children')->get() as $category)
            <h4>{{ $category->name }}</h4>
            @foreach($category->children as $child)
                <span>{{ $child->name }}</span>
            @endforeach
        @endforeach
    </div>
@endAtomicCache

Compression, Chunking & Internals

1. Auto Payload Compression (Gzip > 50KB)

When serialized data exceeds 50KB, AtomicCache compresses it using gzcompress before storing. This reduces Redis memory consumption by 70% to 95% and decompresses transparently on retrieval.

2. Transparent Chunking with MGET Batching

Large collections (1,000+ items) are partitioned into safe chunks ({key}:__chunk__:0, 1). When fetched, all chunks are retrieved in a single batch request via Redis MGET, preventing sequential network roundtrips.

3. Write Deduplication (Cache DNA)

Payloads are hashed before writing. If identical data is already stored, AtomicCache skips redundant store writes and payload compression, refreshing the expiration TTL on the existing item and chunks.

4. Expiry Jitter (withJitter)

Prevents herd expiry spikes when thousands of keys share the same TTL by adding random variance (±5%): 

AtomicCache::withJitter(0.05)->remember('popular_feed', fn() => getFeed(), 3600);

5. Type-Safe Model Tags

Pass Model classes directly to eliminate typos and unlock IDE autocompletion & refactoring safety: 

// 1. Pass Model classes:
AtomicCache::tags([Product::class, Category::class])->remember('catalog', fn() => ..., 3600);

// 2. Pass Model instances (auto-tags "products:12" and "products"):
AtomicCache::tags([$product, 42])->remember('deal', fn() => ..., 3600);

// 3. Clear tags using Model classes:
AtomicCache::clearTags([Product::class, 42]);

Zero-Crash Virtual Tagging

In standard Laravel, calling Cache::tags() on the file or database driver throws an immediate exception. AtomicCache implements a transparent Virtual Tag Engine:

  1. Each tag maintains an integer version key in the store: atomic:__tag_v__:{tag}.
  2. Keys incorporate a hash of their tag versions: {key}:vt:md5(sorted_versions).
  3. Calling AtomicCache::clearTags(['products']) increments the version counter from 1 to 2.
  4. Existing cached entries become instant cache misses in 0 milliseconds, with zero files deleted or slow SQL queries.

CLI Doctor & Benchmarks

1. Model Cache Doctor: php artisan atomic-cache:check

Scans your application models and groups them into three tiers:

  • Active: Models using AutoClearsCache (e.g. Product, Order).
  • Exempt: Models that shouldn't be cached (e.g. ChatMessage, AuditLog, Pivot tables).
  • Recommended: Domain models missing cache traits (e.g. Plan, Category).
php artisan atomic-cache:check --filter=recommended
php artisan atomic-cache:check --json # For CI/CD audit pipelines

2. Benchmark Engine: php artisan atomic-cache:bench

Measures latency, Gzip memory savings, chunking integrity, and tag resilience on your active driver in a structured 5-column breakdown: 

php artisan atomic-cache:bench --driver=redis --iterations=10
+--------------------+------------------------------+-----------------------------------+----------------------+-------------------------+
| Metric Category    | Scenario                     | Raw / Simulated Baseline          | AtomicCache Result   | Improvement / Status    |
+--------------------+------------------------------+-----------------------------------+----------------------+-------------------------+
| ⚡ Latency / Speed | Database Query vs Cache Hit  | 45.00 ms (Simulated DB)           | 0.04 ms              | +99.9% Faster           |
| 📦 Payload Size    | Large Array Gzip Compression | 95.48 KB (Raw Array)              | 4.13 KB (Gzip)       | 95.7% Memory Saved      |
| 🧩 Safe Chunking   | Large Dataset (2,500 items)  | Single raw item (Risk: 1MB limit) | 3 safe chunks        | Passed (Keys Preserved) |
| 🏷️ Tag Resilience  | Non-Redis Virtual Tagging    | Native Tag Support                | Zero-Crash Emulation | Resilient (Zero Crash)  |
+--------------------+------------------------------+-----------------------------------+----------------------+-------------------------+

* Latency speedup is computed against a 45.00 ms simulated MySQL query. Memory savings reflect Gzip compression on structured array payloads (real-world ratio depends on data compressibility).

3. Targeted Tag Purging: php artisan atomic-cache:clear 

php artisan atomic-cache:clear products        # Purges 'products' tag and key
php artisan atomic-cache:clear --all --force   # Force flush entire store without interactive prompt

Caution: Running atomic-cache:clear --all flushes the entire cache store. On shared Redis instances, use with --force only if you intend to clear all cache keys.

API Reference Cheat Sheet & Helpers

Global Helper Function: atomic_cache()

Use the global helper without importing the Facade: 

// 1. Retrieve value or remember
$data = atomic_cache('homepage_banners', 3600, fn() => Banner::all());

// 2. Call fluent builder directly
$data = atomic_cache()->tags([Product::class])->remember('deals', 600, $callback);
Category & Method Signature Return Usage & Best Practice
1. Core Cache Operations (AtomicCache Facade & Helper)
remember($key, $ttl, $callback) mixed Caches computed data. Flexible argument order: supports remember($key, $callback, $ttl) too.
rememberWithLock($key, $ttl, $fn, $tags, $lockSec, $waitSec) mixed Atomic distributed lock protection. Only 1 process computes on cache miss; others wait and read.
rememberForUser($key, $ttl, $fn, $userId = null) mixed Automatically prefixes cache key with auth()->id() or explicit user ID. Isolates private data.
get($key, $default = null, $tags = []) mixed Retrieve cached value directly, or return default fallback.
put($key, $value, $ttl = null, $tags = []) bool Store an item directly. Automatically applies Gzip compression if >50KB and uses write deduplication.
has($key, $tags = []) bool Check if a valid, unexpired key exists in the active cache store.
forever($key, $value, $tags = []) bool Store item with no expiration (useful for static lookup dictionaries).
pull($key, $default = null, $tags = []) mixed Retrieve item and immediately delete it from store (flash data).
forget($key, $tags = []) / clear($key) bool Remove an individual item from cache store.
flush() bool Completely wipe all stored keys from active cache repository.
2. Granular Tag & Resource Invalidation
clearTags($tags) / flushTags($tags) bool Invalidate custom tags across Redis, File, Database, and SQLite stores without crashing.
forgetItem($resource, $id) / clearItem(...) bool Flushes a single item tag (e.g. users:42).
flushCollection($resource) / clearCollection(...) bool Flushes an entire collection tag (e.g. users).
3. Fluent Chainable Builder Methods
AtomicCache::store($driver) AtomicCache Switch driver dynamically (e.g. AtomicCache::store('redis') or 'file').
AtomicCache::tags($tags) AtomicCache Attach tags. Supports string arrays, Product::class, model instance $product, and numeric IDs.
AtomicCache::ttl($seconds) AtomicCache Set explicit Time-To-Live duration in seconds for the fluent chain.
AtomicCache::withLock($lockSec = 10, $waitSec = 5) AtomicCache Attach stampede lock protection to fluent builder chain.
AtomicCache::forUser($userId = null) AtomicCache Scope fluent operation to authenticated user or specified user ID.
AtomicCache::withJitter($percentage = 0.05) AtomicCache Add random variance (±5%) to TTL to prevent simultaneous expiry spikes.
4. Eloquent & DB Query Macros
->atomicCache($keyOrTtl = null, $ttl = null, $tags = [], $lock = false) Collection List queries with automatic key fingerprinting and table tagging (defaults to configured TTL).
->atomicCacheFirst($keyOrTtl = null, $ttl = null, $tags = [], $lock = false) Model | null Single-item queries with optional stampede lock protection (defaults to configured TTL).
5. Blade Directives & Helpers
@atomicCache('key', $ttl, $tags) ... @endAtomicCache HTML Cache rendered HTML templates, menus, and sidebars directly in Blade.
atomic_cache(?string $key = null, mixed $arg2 = null, mixed $arg3 = null) mixed Global shortcut helper for instance, retrieval, or remembering values.
6. Service Layer (HasAtomicCache Trait)
$this->cache($method, $args, $callback, $ttl, $perUserOrTags, $lock) mixed Declarative argument hashing for any service method. Normalizes Closures, Models, and queries.
$this->rememberItem($id, $callback, $ttl) / cacheItem(...) mixed Remembers a single entity by ID under {resource}:{id} item tag.
$this->rememberCollection($key, $callback, $ttl) / rememberList(...) mixed Remembers a list query under {resource} collection tag with query isolation.
$this->forgetItem($id) / clearItemCache($id) bool Flushes a single item cache tag from within the service.
$this->flushCollection() / clearCollectionCache() bool Flushes the entire collection cache tag for this service resource.
$this->flushAll() / clearAllCache() bool Flushes all cache tags related to this service resource.
