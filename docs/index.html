Docs Getting Started Introduction

Introduction

thekaziomar/laravel-atomic-cache is an open-source caching engine for Laravel applications facing real-world traffic surges. Built with full support for Laravel 10.x, 11.x, 12.x, and 13.x, it prevents cache stampedes, enables tag-based invalidation across non-Redis stores without crashing, and keeps database load predictable.

Laravel 10 / 11 / 12 / 13.x PHP 8.2 / 8.3 / 8.4 Zero Redis Required (Works on File & DB)
Drop-in Replacement: You do not need to rewrite your application. You can continue using standard Laravel cache syntax, or use rememberWithLock() where high concurrency protection is needed.

Here is what it looks like in practice:

app/Services/ProductService.php 
use KaziOmar\AtomicCache\Facades\AtomicCache;
use App\Models\Product;

// Stampede-proof caching: Only 1 query hits MySQL, even with 1,000 concurrent shoppers
$products = AtomicCache::tags(['products'])
    ->rememberWithLock('trending_catalog', 3600, function () {
        return Product::where('is_featured', true)
            ->with('category')
            ->take(20)
            ->get();
    });

Why This Exists: The NovaMart Store Story

To understand why this package was created, consider NovaMart — a real e-commerce store running on Laravel with 25,000 products and active promotional campaigns.

Under gentle traffic, Laravel's default Cache::remember() works fine. But during seasonal promotions and traffic spikes, four specific failures frequently cause production downtime:

1. Midnight Cache Stampede (Dogpiling)

When the 1-hour cache for the catalog expires at 12:00:00 AM, 1,200 active shoppers hit the page simultaneously. Instead of 1 query, Laravel fires 1,200 identical queries to MySQL at the exact same millisecond. Connections max out, resulting in 504 Gateway Timeouts.

2. Tag Crash on Local & Staging Environments

Developers use Cache::tags(['products']) on production with Redis. But when running tests or local development with the file or database cache driver, the app crashes with BadMethodCallException: This cache store does not support tagging.

3. Ad Link Cache Fragmentation

Marketing campaigns bring traffic with query strings like ?utm_source=fb&fbclid=xyz. Standard URL caching treats each click as a brand new page, generating thousands of duplicate cache files for the exact same product and wasting RAM.

4. Memory Exhaustion on Large Catalogs

Serializing large catalog arrays (5,000+ items) into Redis or Memcached exhausts memory buffers or hits the 1MB Memcached packet limit. AtomicCache solves this with transparent Gzip compression and multi-chunk partitioning.

Who Is This For?

This package is built for engineering teams that need reliable caching without unnecessary operational overhead:

  • E-commerce & Marketplaces: High catalog reads, flash sales, and cart checkouts where database spikes must be contained.
  • SaaS Dashboards: Endpoints with expensive aggregations, analytics, or recurring billing summaries.
  • Teams Using Multiple Drivers: Applications that use Redis in production, but prefer SQLite or File stores in local dev and GitHub Actions CI pipelines.

Honest Limitations: When NOT To Cache

No caching tool solves every use case. Here is where you should never use caching:

  • Real-time WebSockets & Chat Messages: Chat messages (`ChatMessage`) stream directly via Pusher/Reverb. Caching them creates memory churn without read benefits.
  • High-Frequency GPS Telemetry: Live rider location updates sent every 3 seconds should stream into Redis Pub/Sub, Kafka, or ClickHouse, not application-level cache.
  • Audit Logs: Immutable append-only audit records (`AuditLog`) are write-heavy and must be written directly to the database.

Quick Installation

Install the package via Composer into any Laravel 10, 11, 12, or 13 project:

terminal 
composer require thekaziomar/laravel-atomic-cache

Configuration (Optional)

Publish the optional configuration file if you want to customize lock durations, compression thresholds, or key prefixes:

terminal 
php artisan vendor:publish --tag="atomic-cache-config"

Zero-Key Query Macros: Method Signatures & Parameters

atomic-cache attaches fluent macros directly to Laravel's Eloquent and Query builders: ->atomicCache() and ->atomicCacheFirst().

Method Signatures 
// 1. For Collection queries (get / all)
$builder->atomicCache($keyOrTtl = 3600, $ttl = null, array $tags = [], bool $lock = false)

// 2. For Single-Record queries (first / find)
$builder->atomicCacheFirst($keyOrTtl = 3600, $ttl = null, array $tags = [], bool $lock = false)

Parameter Deep Dive: When, Why & How

Parameter Type Default Purpose & Recommendation
$keyOrTtl int | string 3600 Dual-mode argument: Pass an integer like 3600 to set TTL with automatic deterministic SQL fingerprinting. Or pass a string like 'homepage_deals' to force a custom cache key.
$ttl int | null null TTL in seconds. Only needed if you passed a custom string key as the 1st parameter (e.g. ->atomicCache('deals', 1800)).
$tags array [] Extra tags. The macro already tags the model's table name automatically (e.g. products). Use this only if you want cross-entity group tags like ['homepage', 'seasonal_sale'].
$lock bool false Distributed Mutex Lock. When set to true (or in atomicCacheFirst(5, lock: true)), it acquires an atomic lock when the cache expires. Always set to true on high-traffic endpoints and flash sales!

Real-World Usage Examples in NovaMart: 

// Example 1: 100% Zero-Key with 1-hour TTL (Standard Catalog)
$products = Product::where('is_active', true)
    ->where('stock', >, 0)
    ->atomicCache(3600);

// Example 2: High Concurrency Flash Sale Product (5 seconds TTL + Distributed Lock)
// 5,000 shoppers hitting this at 8:00 PM only cause 1 single database query!
$deal = Product::where('id', $productId)
    ->atomicCacheFirst(5, lock: true);

// Example 3: Table Alias Normalization
// "orders as o" is safely normalized to "orders" tag automatically!
$orders = DB::table('orders as o')
    ->where('o.status', 'completed')
    ->atomicCache(600);

Model Auto Invalidation: Static vs Dynamic Tags

The AutoClearsCache trait hooks into Eloquent lifecycle events (created, updated, deleted, and restored) strictly inside DB::afterCommit(). If a transaction rolls back, your cache remains 100% untouched.

app/Models/Product.php 
namespace App\Models;

use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\SoftDeletes;
use KaziOmar\AtomicCache\Traits\AutoClearsCache;

class Product extends Model
{
    use AutoClearsCache, SoftDeletes;

    // 1. Static related tags (fixed strings)
    protected array $relatedCacheTags = ['homepage_featured', 'catalog_filters'];

    // 2. Dynamic related tags (based on model attributes like store_id or category_id)
    public function getRelatedCacheTags(): array
    {
        return [
            "stores:{$this->store_id}:products",
            "categories:{$this->category_id}",
        ];
    }
}

Service Layer Caching: Consistent Architecture

In enterprise applications, caching belongs inside dedicated Service classes. The HasAtomicCache trait provides a standard 2-step caching formula for every method:

app/Services/CatalogManager.php 
namespace App\Services;

use KaziOmar\AtomicCache\Traits\HasAtomicCache;
use App\Models\Product;

class CatalogManager
{
    use HasAtomicCache;

    // 💡 Custom Resource Rule: If the class name (CatalogManager) does not match
    // the database table (products), override $cacheResource to bind them together!
    protected string $cacheResource = 'products';
    protected int $cacheTTL = 3600;              // Default 1 hour
    protected bool $cachePerUser = false;         // Global public catalog

    public function getById(int|string $id, array $with = [])
    {
        $callback = fn() => Product::with($with)->findOrFail($id);
        return $this->cache(__FUNCTION__, func_get_args(), $callback, $this->cacheTTL, $this->cachePerUser);
    }

    public function getByCategory(int $categoryId, int $perPage = 20)
    {
        $callback = fn() => Product::where('category_id', $categoryId)
            ->where('is_active', true)
            ->paginate($perPage);

        return $this->cache(__FUNCTION__, func_get_args(), $callback, $this->cacheTTL, $this->cachePerUser);
    }
}

User-Scoped Caching: Private Data Isolation

In shopping carts, customer wishlists, and personalized financial dashboards, caching under a global key causes catastrophic data leaks where User A sees User B's cart.

Use rememberForUser() to automatically prefix the cache key with the authenticated user's ID: 

use KaziOmar\AtomicCache\Facades\AtomicCache;
use App\Models\Cart;

// Automatically scopes cache to auth()->id() (e.g. "user:42:user_cart")
$cart = AtomicCache::rememberForUser('user_cart', 600, function () {
    return Cart::where('user_id', auth()->id())
        ->with('items.product')
        ->first();
});

Flash Sale Architecture: 10 Stock vs 5,000 Users

The ultimate e-commerce test: NovaMart launches a Flash Sale with exactly 10 units of an iPhone. 5,000 shoppers click "Buy Now" at the exact same millisecond.

app/Http/Controllers/FlashSaleController.php 
namespace App\Http\Controllers;

use Illuminate\Support\Facades\DB;
use App\Models\Product;
use App\Models\Order;

class FlashSaleController
{
    // STEP 1: READ SHIELD - 5,000 users refreshing the product page
    // Zero-key query macro with 5s TTL + lock absorbs 5,000 requests into 1 single query!
    public function show(int $productId)
    {
        return Product::where('id', $productId)
            ->atomicCacheFirst(5, lock: true);
    }

    // STEP 2: WRITE SHIELD - Atomic Row Locking prevents overselling
    public function checkout(int $productId, int $userId)
    {
        return DB::transaction(function () use ($productId, $userId) {
            // 1. Lock the Eloquent row in MySQL to serialize concurrent checkouts
            $product = Product::where('id', $productId)
                ->lockForUpdate()
                ->firstOrFail();

            if ($product->stock < 1) {
                return response()->json(['error' => 'Sold out!'], 422);
            }

            // 2. Decrement inventory safely
            $product->decrement('stock', 1);

            // 3. Record valid order
            $order = Order::create([
                'user_id' => $userId,
                'product_id' => $productId,
                'status' => 'confirmed'
            ]);

            // 4. AutoClearsCache trait on Product automatically hooks into DB::afterCommit()
            // and purges 'products' and "products:{$productId}" cache tags across all stores.
            // Exactly 10 orders succeed; remaining 4,990 instantly see "Sold out!"
            return response()->json(['success' => true, 'order_id' => $order->id]);
        });
    }
}

Virtual Tagging: How File & Database Stores Work

When you call AtomicCache::tags(['products']) on non-Redis stores (File, SQLite, Database), the package does not bypass caching or throw exceptions:

  1. Each tag has an integer version key in store: atomic:__tag_v__:{tag}.
  2. When storing data, it generates a composite hash: key:vt:md5(sorted_tag_versions).
  3. Calling AtomicCache::clearTags(['products']) increments the tag version from 1 to 2.
  4. Instantly, all old keys point to outdated hashes and are invalidated in 0ms without deleting files or running expensive SQL queries!

Production Health Auditor & Benchmarks

Audit your application models before deployment with built-in Artisan diagnostics: 

# Audit all Eloquent models & calculate architecture health score
php artisan atomic-cache:check

# Filter only models that need attention
php artisan atomic-cache:check --filter=recommended

# Output as JSON for CI/CD pipelines
php artisan atomic-cache:check --json

# Run throughput benchmark on your active cache driver
php artisan atomic-cache:bench

Auditor Classification Tiers:

  • Active (Green): Models using AutoClearsCache (e.g. Product, Order).
  • Exempt (Cyan): Models that SHOULD NOT be cached (e.g. ChatMessage, AuditLog, telemetry).
  • Recommended (Yellow): High-read models missing cache traits (e.g. Category, Plan).

Complete API Reference Cheat Sheet

Method Signature Return When To Use When To Avoid
->atomicCache($ttl) Collection Database list queries with automatic key & table tagging. Real-time WebSocket streaming or append logs.
->atomicCacheFirst($ttl, lock: true) Model | null Single item queries under heavy concurrent traffic (flash sales). Multi-record collection queries.
rememberWithLock($key, $ttl, $fn) mixed Expensive reports, slow aggregations, traffic burst spikes. Extremely light queries where locking adds unnecessary overhead.
rememberForUser($key, $ttl, $fn) mixed Private carts, user profiles, personal financial stats. Public catalog data shared across all customers.
tags([Product::class]) self Type-safe tag grouping with IDE autocompletion. Typo-prone raw strings.
clearTags($tags) bool Targeted invalidation across Redis, File, SQLite and Database. Global cache flushing.
