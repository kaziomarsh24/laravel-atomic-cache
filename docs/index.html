Getting Started  /  Overview

Laravel Atomic Cache

thekaziomar/laravel-atomic-cache is an enterprise-grade caching and invalidation engine for Laravel. Built specifically for Laravel 10.x, 11.x, 12.x, and 13.x, it solves four critical production challenges: cache stampedes during concurrent spikes, crashes when using cache tags on non-Redis stores, stale data caused by database transaction rollbacks, and memory exhaustion from oversized datasets.

Laravel 10 / 11 / 12 / 13.x PHP 8.2 to 8.5 Redis, Memcached, File, Database, DynamoDB & SQLite
Drop-in Familiarity
You do not need to rewrite your application or learn proprietary query syntax. You can use your existing Eloquent models, Query Builder calls, and repository methods. AtomicCache silently manages fingerprinting, mutex locking, Gzip compression, and transaction-safe invalidation behind the scenes.

Architectural Philosophy: Core-First Caching

Laravel Atomic Cache is organized into a clean 3-tier Core-First Architecture. Rather than coupling you to heavy abstractions, the foundations are completely self-contained:

Tier 1: Optional Syntactic Sugar
->atomicCache() HasAtomicCache @atomicCache
Tier 2: Eloquent Model Lifecycle Layer (AutoClearsCache)

created / updated / deleted / restored  -->  DB::afterCommit

Tier 3: The Core Engine (AtomicCache::)

Distributed Locks • Virtual Tags • Gzip Compression • Universal OCC • Generation Chunking • Self-Healing • Expiry Jitter • Transaction Guard

The Core Engine (`AtomicCache::`) is completely self-contained. While query macros and traits provide convenient shortcuts, you can build your entire application directly with the Core Engine for explicit and predictable control.

Why AtomicCache?

Under low traffic, standard Cache::remember() works fine. But under real-world production load, several systemic failures emerge. Here is how AtomicCache compares with standard Laravel cache:

Feature Standard Laravel Cache Laravel Atomic Cache
Stampede Protection None (Concurrent requests hit DB) Atomic Lock (1 worker computes, others wait & read)
Large Payload Size Raw uncompressed serialization Auto Gzip (>50KB cuts Redis RAM by up to 70–80%)
Mega Datasets Fails on 1MB Memcached limit / network buffer Transparent Chunking (partitions safely across chunks)
Redundant Writes Every put writes to cache store Write Deduplication (skips re-compression & splitting)
Driver Tag Support Crashes on File/Database stores Virtual Tagging (works across all stores without Redis)
Corrupted Data Throws crash exception to user Self-Healing (cleans key, regenerates silently)
Simultaneous Expiry All keys expire in same second TTL Jitter (random variance prevents herd spikes)
Model Invalidation Fragile observers before commit DB::afterCommit (prevents transaction race conditions)
Query Caching Manual key hashing required Zero-Key Macros (auto SQL + eager load fingerprinting)
Architecture Audit Manual DIY logging Artisan Doctor CLI (atomic-cache:check)

Who Is This For?

AtomicCache is engineered for teams building resilient applications where database saturation and cache inconsistency directly impact business revenue:

  • E-commerce & Flash-Sale Platforms: Prevent database crashes when 10,000 buyers simultaneously refresh promotional categories or product catalogs.
  • SaaS Products & Analytics Dashboards: Cache complex aggregation queries, tenant-scoped metrics, and multi-tenant billing summaries with zero cross-tenant contamination.
  • Teams Developing on Local / File / SQLite: Write tag-based caching logic seamlessly in local development and automated testing environments without needing a live Redis server running.
  • High-Throughput Content Portals: Maintain flat, predictable database CPU utilization during massive traffic spikes or viral social media referral traffic.

When NOT to Cache & Anti-Patterns

Caching is not suitable for every data model. Avoid caching in these specific scenarios:

  • Real-time WebSockets & Chat Messages: Chat messages (e.g. ChatMessage) should be broadcasted directly via Pusher or Laravel Reverb. Caching them creates unnecessary memory churn without read benefits.
  • High-Frequency GPS & Telemetry: Live rider location updates sent every 3 seconds belong in Redis Pub/Sub, Kafka, or ClickHouse, not application-level cache.
  • Audit Ledgers & Financial Balances: Financial transactions and audit logs are write-heavy and must be queried directly from the authoritative database with row locks.

Architectural Limitations & Gotchas

1. Eloquent Mass Operations (Bypasses Model Events)

Direct query builder batch updates or deletes (e.g. Product::where(...)->update(...), delete(), insert()) do not fire Eloquent model events. Consequently, AutoClearsCache will not automatically trigger.

app/Services/ProductService.php
1
2
3
4
5
6
7
8		 // Warning: Mass query builder updates do not fire Eloquent model events: Product::where('category_id', 5)->update(['status' => 'archived']); // Solution 1: Use the model's static flush helper: Product::flushCache(); // Solution 2: Clear the model table tag via facade: AtomicCache::clearCollection('products'); // or AtomicCache::clearTags([Product::class]);

2. Pagination with Query Macros (->atomicCache())

The ->atomicCache() macro immediately terminates the query and executes ->get(), returning an Eloquent Collection. You cannot chain ->paginate() afterwards.

app/Services/ProductService.php
1
2
3
4
5
6
7		 // Recommended: Use HasAtomicCache in your Service Layer // rememberCollection() automatically isolates request query strings and page numbers: class ProductService { use HasAtomicCache; public function getActiveProducts() { return $this->rememberCollection('active', fn() => Product::where('status', 'active')->paginate(15), 3600); } }

Guarantees vs Non-Guarantees

To ensure complete clarity on what AtomicCache handles automatically versus what requires developer attention:

Scenario / Operation Automated by Package? Behavior & Action Required
Eloquent Model Instance Save: $product->save(), update() Yes Automatically flushes item tag (products:42), collection tag (products), and parent relations strictly on DB::afterCommit.
Model Deletes & Restores: $product->delete(), restore() Yes Automatically flushes related tags on DB::afterCommit.
Model Counters: $product->increment(), decrement() Yes Fires updated model event; automatically clears cache on commit.
Single-Level BelongsTo Parents: $cacheParents = ['store'] Yes Automatically clears child tag, scoped tag (stores:5:orders), and parent umbrella tag (stores:5).
Active Transactions: DB::transaction() Yes AtomicCache::remember() automatically bypasses cache during active transactions to prevent dirty reads and phantom cache on rollbacks.
High-Frequency Columns: $cacheIgnoreColumns Yes Updating counters (e.g. view_count) clears only the single item tag (products:5) and keeps table and parent collections warm.
Rolled-back Transactions: DB::rollBack() Yes Invalidation callbacks are deferred to afterCommit. If rollback occurs, cache is untouched.
Query Builder Mass Updates: Product::where()->update() No Eloquent events do not fire. You must manually call Product::flushCache(); or AtomicCache::clearCollection('products').
Query Builder Mass Deletes: Product::where()->delete() No Eloquent events do not fire. Call Product::flushCache(); manually.
Direct SQL / DB Facade: DB::table('products')->delete() No Bypasses Eloquent entirely. Call AtomicCache::clearCollection('products') manually.
Quiet Operations: saveQuietly(), withoutEvents() No Intentionally suppresses model events. Call $product->clearCache() manually if needed.
Pivot Table Changes: attach(), detach(), sync() No Pivot mutations do not fire model events on parent models. Call AtomicCache::clearTags(...) manually.
Multi-Level Grandparent: Item -> Order -> Store No Laravel's native $touches calls rawUpdate() which does NOT fire model events. Either manually call $orderItem->order->touch() or declare parent tags via getRelatedCacheTags().
External Database Mutations: External scripts, ETL imports No External processes outside PHP cannot trigger Laravel events. Schedule or invoke cache invalidation manually.

Architecture Layer 1

The Core Caching Engine (AtomicCache::)

The `AtomicCache` facade provides manual, high-performance caching with distributed concurrency controls.

1.1 Basic Caching & CRUD

Works intuitively like native Laravel cache, supporting flexible parameter ordering:

1
2
3
4
5
6
7		 // Standard signature: remember($key, $ttl, $callback) or remember($key, $callback, $ttl) $posts = AtomicCache::remember('posts.all', 3600, fn() => Post::where('published', true)->get()); // Standard CRUD operations: AtomicCache::put('settings', $settings, 86400); // Store directly $value = AtomicCache::get('settings'); // Retrieve AtomicCache::forget('settings'); // Delete single key
What breaks it: Passing non-positive TTLs (0 or negative) will not cache the item; it immediately calls forget() and deletes the key. Passing closures returning open resources (like PDO instances or curl handles) causes serialization failure.

1.2 Stampede Protection (rememberWithLock)

Acquires an atomic distributed lock via Laravel's LockProvider. Only 1 process calculates the value, while all other concurrent requests wait and read the fresh cache via Double-Checked Locking:

1
2
3		 $stats = AtomicCache::rememberWithLock('annual_report', 86400, function () { return HeavyReportingService::calculate(); }, lockSeconds: 15, waitSeconds: 5);

1.3 Virtual Tagging Engine

On non-taggable drivers (File, Database), embeds UUID version tokens into cache keys. Invalidation happens in 0ms without deleting individual files from disk:

1
2
3
4		 $catalog = AtomicCache::tags(['products', 'categories']) ->remember('catalog_active', 3600, fn() => Product::all()); AtomicCache::clearTags(['products']); // Invalidates instantly across File, DB, and Redis!

1.4 Manual Invalidation Methods

1
2
3
4		 AtomicCache::clearCollection('products'); // Flushes tag 'products' AtomicCache::clearItem('products', 42); // Flushes tag 'products:42' AtomicCache::clearTags(['products', 'stores:5']); // Flushes custom tags AtomicCache::forget('custom_key'); // Deletes specific key
Warning on shared cache stores: Calling AtomicCache::flush() without active tags will flush the raw underlying cache store. On shared Redis instances, this will purge user session data! Always use clearTags() or clearCollection().

1.5 Payload Compression (Gzip > 50KB)

Whenever serialized data exceeds 50 KB, AtomicCache compresses it using gzcompress before storing. This reduces Redis memory consumption by up to 70–80% and decompresses transparently on retrieval.

1.6 Transparent Chunking (Mega Datasets)

Arrays and Collections exceeding 1,000 items (or 800 KB estimated payload) are automatically partitioned across driver-safe chunk keys under unique **Generation UUIDs**, eliminating torn-read race conditions and complying with Memcached's 1MB limit.

1.7 Cache TTL Jitter (withJitter)

Prevents thundering herd expiry spikes by applying random variance (±5%) to the TTL:

1 AtomicCache::withJitter(0.05)->remember('popular_feed', 3600, $callback);

1.8 User-Scoped Caching (rememberForUser)

Automatically scopes keys under atomic:user:{id}:{key}, supporting integer IDs, UUIDs, and ULIDs:

1 $cart = AtomicCache::rememberForUser('cart', 1800, fn() => Cart::where('user_id', auth()->id())->first());

1.9 Write Deduplication (Cache DNA)

When enabled (ATOMIC_CACHE_DEDUPLICATION_ENABLED=true), AtomicCache hashes serialized data before writing. If identical content is already cached, it skips CPU-intensive Gzip re-compression and chunk re-splitting, refreshing the TTL in storage.

1.10 Optimistic Concurrency Control (OCC)

Captures tag version tokens before and after invoking remember closures. If another process invalidates tags while a slow computation was running, the stale result is safely discarded instead of repopulating freshly cleared cache keys.

1.11 Self-Healing Engine

If a cached payload is corrupted or missing a chunk, AtomicCache catches the deserialization exception, logs the event, purges the broken key, and silently recomputes fresh data from the callback without crashing user requests.

1.12 Transaction Guard & Testing Warning

When bypass_during_transactions is enabled (default: true), AtomicCache detects active database transactions across all open connections. During transactions, remember() bypasses cache reading and writing, running the query directly to prevent phantom caches on rollbacks.

Critical Testing Warning (RefreshDatabase & DatabaseTransactions)

If your feature tests use Laravel's RefreshDatabase trait, tests run inside an uncommitted transaction (transactionLevel() === 1). Cache remember() will always bypass cache by default during those tests!

<env name="ATOMIC_CACHE_BYPASS_DURING_TRANSACTIONS" value="false"/>

Add the line above to your phpunit.xml to test cache hits inside transactional tests, or call AtomicCache::withoutTransactionBypass()->remember(...).

Architecture Layer 2

Eloquent Model Lifecycle (AutoClearsCache)

2.1 DB::afterCommit Auto Invalidation

Hooks into created, updated, deleted, and restored. Defers cache flushing strictly to DB::afterCommit. If a transaction rolls back, your cache is 100% untouched:

1
2
3
4		 use KaziOmar\AtomicCache\Traits\AutoClearsCache; class Product extends Model { use AutoClearsCache; }

2.2 Declarative Parent Invalidation ($cacheParents)

Declare parent relationships to automatically cascade invalidation up the tree:

1
2
3
4
5
6
7		 class Order extends Model { use AutoClearsCache; // Automatically flushes parent store caches on commit protected array $cacheParents = ['store']; public function store(): BelongsTo { return $this->belongsTo(Store::class); } }

2.3 Manual Flush Helpers (flushCache & clearCache)

1
2
3
4		 // 1. Instance helper: manually clear single record and parents $product->clearCache(); // 2. Static helper: flush entire table tag for this model Product::flushCache();

2.4 High-Frequency Column Protection ($cacheIgnoreColumns)

Updating counters (e.g. view_count) clears only the single item tag (products:42) while keeping collection tags warm:

1
2
3
4		 class Product extends Model { use AutoClearsCache; protected array $cacheIgnoreColumns = ['view_count', 'meta']; }

2.5 Strict Mode for Parent Relations (strict_mode)

When enabled (default in local environment), invalid $cacheParents declarations (typos, passing classes instead of methods, non-BelongsTo relations) immediately throw descriptive InvalidArgumentException exceptions. In production, it logs a warning safely.

2.6 Transaction-Safe Bulk Invalidation (invalidating)

1
2
3
4		 AtomicCache::invalidating([Order::class, Product::class], function () { DB::table('orders')->where('status', 'draft')->delete(); DB::table('products')->where('stock', 0)->update(['status' => 'out_of_stock']); });

Uses a try/finally guarantee: outside a transaction, invalidation is guaranteed even if the closure throws an exception, preventing stale reads after partial database mutations. Inside an active transaction, invalidation is safely registered via DB::afterCommit(). If the transaction rolls back, cache is untouched.

2.7 Rules & What Breaks Model Invalidation

  • Mass queries bypass model events: Product::where(...)->update() or delete() does not fire Eloquent events. Call Product::flushCache(); after updates.
  • Quiet saves suppress events: saveQuietly() requires calling $product->clearCache() manually.
  • Pivot table changes: Many-to-many sync(), attach(), or detach() requires calling AtomicCache::clearTags([Product::class, Category::class]).
  • $cacheParents only supports BelongsTo: Declaring hasMany or morphTo throws InvalidArgumentException in strict mode or logs a warning in production.
  • Custom owner keys are skipped: Relations using custom owner keys (e.g. string slugs) are skipped to avoid mismatched umbrella tags.
  • Grandparents and Laravel $touches: Laravel's native protected $touches = ['order'] runs raw SQL and DOES NOT fire events! Either call $orderItem->order->touch() directly or define getRelatedCacheTags().
Architecture Layer 3

Query Builder Macros (->atomicCache())

3.1 Zero-Key Query & First Record Caching

1
2
3
4		 // Fingerprints SQL, bindings, and eager loads automatically: $featured = Product::where('status', 'active')->latest()->atomicCache(3600); $product = Product::where('slug', $slug)->atomicCacheFirst(3600); $scoped = Order::where('store_id', 5)->atomicCache(scope: 'stores:5:orders');

3.2 Critical Rules & What Breaks Query Macros

  • Do not chain ->paginate() after ->atomicCache(): The macro terminates the query with ->get(). Use HasAtomicCache::rememberCollection() for pagination.
  • Mass updates will not clear query macro caches: Product::where(...)->update() does not clear the cache. Call Product::flushCache(); after updates.
  • scope: queries and mass updates: Order::flushCache() only clears base table tags. Scoped queries (scope: 'stores:5:orders') must be cleared explicitly: AtomicCache::invalidating(['stores:5:orders', Order::class], fn() => ...);.
  • scope: queries omit automatic joins: When scope: is passed, join-table tagging is omitted in favor of the scope. Model lifecycle invalidation requires a declared $cacheParents relation.
  • Eager loading does not auto-tag related tables: Product::with('category')->atomicCache() fingerprints relations, but does not auto-tag related tables. Pass related tags explicitly: tags: ['categories'].
  • Raw SQL subqueries are not auto-tagged: Tables inside joinRaw() or subqueries must be passed explicitly in tags: ['categories'].

Engine Internals

Zero-Crash Virtual Tagging

In standard Laravel, calling Cache::tags() on the file or database driver throws an immediate BadMethodCallException. AtomicCache implements a transparent Virtual Tag Engine:

  1. Each tag maintains a unique UUID version token in the store: atomic:__tag_v__:{tag}.
  2. Keys incorporate an MD5 hash of their sorted tag tokens: {key}:vt:md5(sorted_tokens).
  3. Calling AtomicCache::clearTags(['products']) generates a fresh UUID token in the store atomically.
  4. Existing cached entries become instant cache misses in 0 milliseconds without running slow directory scans or SQL deletes.
Engine Internals

Distributed Locking & Universal OCC

Double-Checked Locking: When acquiring a lock, AtomicCache re-checks the cache before executing the closure. If another process computed the result while this worker was waiting, it immediately returns the fresh cache.

Universal OCC: Tag version tokens are captured before and after computing remember closures. If another process invalidates tags mid-computation, the stale write is safely discarded.

Engine Internals

Compression & Generation UUID Chunking

Auto Gzip (>50KB): Reduces memory footprint by up to 70–80% for large collections and decompresses transparently on retrieval.

Generation UUID Chunking: Mega datasets (1,000+ items or 800 KB ceiling) are partitioned across safe chunk keys. All chunks are published under a unique generation UUID before the manifest pointer updates atomically, preventing concurrent readers from reading partial/torn data.

Troubleshooting & FAQ

1 The cache is not cleared after updating data

• Mass Updates: Product::where()->update() bypasses events. Call Product::flushCache(); after updates.
• Quiet Saves: saveQuietly() suppresses events. Call $product->clearCache() manually.
• Pivot Changes: sync() requires calling AtomicCache::clearTags([User::class, 'roles']).
• Transaction Rollback: AutoClearsCache uses afterCommit. Rolled-back writes never invalidate cache.

2 The cache never hits (always a cache miss)

• Disabled in .env: Check if ATOMIC_CACHE_ENABLED=true.
• Dynamic Timestamps: where('created_at', '<=', now()) changes every second. Round to 5-minute boundaries.
• Query DoS Limits: Requests with >20 parameters bypass cache. Adjust query_limits.max_params in config.
